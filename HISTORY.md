# Persistent execution history

Start with `--enable-history` to retain terminal workflow history and output references across process restarts. It uses the existing local SQLite database (`--database-url`, default `comfyui.db` in the user directory). Assets scanning is independent: `--disable-assets --enable-history` retains history without scans. A file-backed SQLite URL is required.

`--history-limit N` keeps the newest N completed records (default 10000). Replacing a prompt ID keeps its position. Without `--enable-history`, existing in-memory behavior remains unchanged, including its effective 10001-record limit. Disabling persistence leaves saved records untouched; re-enabling restores them.

The history and jobs APIs expose restored records and workflow associations. Deleting or clearing history commits the entire request atomically; storage failures return HTTP 503 and leave memory unchanged. The existing frontend may refresh retained items without showing an error notification when deletion fails; API clients should check the HTTP status. History deletion does not delete generated files, asset entries, backups, SQLite free pages or WAL contents. Missing output files remain historical references. Queued computation is not resumed.

Persistence is opt-in because prompts, workflow widget values and custom outputs may contain sensitive content. Known `auth_token_comfy_org` and `api_key_comfy_org` mapping fields are removed recursively before storage. Error input values, tracebacks and arbitrary exception text are not retained; event names, timestamps and node information remain. This does not guarantee arbitrary strings or custom content are secret-free.

Records must be finite JSON and at most 100 MiB encoded. Unsupported custom objects or oversized records are rejected, never truncated. These failures do not fail generation. If validation, projection or the size limit rejects a record, memory retains only a terminal marker with the prompt ID and validated status; workflow, output references, messages and original queue priority are unavailable. A database failure after projection retains the sanitized record in memory. In either case, `history_persistence` in `/system_stats` reports sticky `healthy:false` and an incremented `failure_count`. Earlier failed saves stay degraded after later successful saves. Memory-only results can disappear on restart; saved records evicted only from memory after a failed save can reappear. Logs report fixed reason codes such as `unsupported_json`, `record_too_large` or `database_locked`, without exception text or SQL parameters. Check the reason and database availability. No delayed retry can resurrect records after a successful clear.

Startup refuses incompatible or corrupt retained records rather than silently discarding them. If the legacy database cannot be relocated because its WAL cannot be checkpointed, startup stops without creating a new empty database; stop the other process and retry. Preserve the database and backups during recovery: workflow history cannot be reconstructed by rescanning output files. Existing SQLite WAL/NORMAL settings support ordinary process-restart recovery, not guaranteed survival of recent commits during power failure.

Serialization and database commits add per-completion latency. History mutations are serialized, while queue/history reads use a short memory lock and remain available during database contention. History GETs read bounded memory rather than querying SQLite each time.
